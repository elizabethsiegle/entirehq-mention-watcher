## B. Task quality

**Important**
- **`scripts/watch.mjs`, `pollOnce` (the `saveStore` call precedes the `for…await announce` loop):** because *all* of `fresh` is marked seen before any of it is announced, a process crash/kill mid-loop (not just a Slack-post failure) silently drops the unannounced tail of the batch — those tweets are never shown in the terminal *or* posted to Slack, and restart won't retry them since they're already in `seen`. The code's inline comment justifies this tradeoff only for a single failed Slack post; here it extends to losing entire mentions (terminal included) on any process death mid-batch. Narrow window, but the consequence is a silently missed mention — the one thing this tool exists to catch.

**Minor**
- **`backoffMs()` / catch block in `loop()`:** `consecutiveFailures` is incremented *before* `backoffMs()` is called, so the first retry after one failure waits `pollMs × 2¹` (double), not `pollMs × 2⁰`. Still exponential, still capped, still resets on success — just skips the base-interval term. Not a spec violation (brief doesn't pin exact values), just worth a note.
- **Double signal (`SIGINT`/`SIGTERM` twice quickly):** `shutdown()` isn't guarded against re-entry — a second signal reprints `mention watcher stopped` and calls `process.exit(0)` again. Harmless (second `exit` is a no-op), but not idempotent.
- **Report's "oldest-first" ordering claim** isn't actually enforced by this file — order is whatever `scrapeSearch`/`filterAndClassify`/`diffSeen` produced. Not a functional defect, just an unverified claim in the report text.
